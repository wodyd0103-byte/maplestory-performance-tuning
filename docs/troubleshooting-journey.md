# 진단 여정 — 상세 기록

증상 신고부터 원인 확정까지의 전 과정. **각 단계의 가설 → 측정 → 결과 → 판단(및 오판)** 을 순서대로 남긴다.

결과만 보면 "RAM이 부족했다"는 한 줄이지만, 거기 도달하는 데 9단계가 걸렸고 그중 5개 가설이 틀렸다. 틀린 경로를 남기는 게 이 문서의 목적이다.

---

## 0. 처음의 고민

> "전략적 팀 전투 + 메이플스토리 + 피파온라인 감독모드 + 크롬 같이 실행하면 버거울 정도인지 확인 부탁해"

게임 3개와 브라우저를 동시에 켜고 쓰는 환경. 실제로 겪던 증상은 두 가지였다.

| 증상 | 체감 |
|---|---|
| **프레임 드랍** | 메이플 사냥 중 화면이 끊김 |
| **프리징** | 수 초간 완전히 멈춤 |
| 관찰 | 작업관리자에서 CPU·GPU·RAM이 90~100%로 보임 |

이 두 증상을 **하나의 문제로 뭉뚱그린 것**이 초반 혼선의 원인이었다. 결과적으로 둘은 원인이 전혀 달랐다.

---

## 1단계 — 사양 확인, 그리고 첫 오판

### 측정

| 부품 | 값 |
|---|---|
| CPU | i5-12600K (P6 + E4, 16스레드) |
| RAM | 32GB (8GB × 4) |
| GPU | RTX 3080 Ti 12GB |
| 저장소 | Samsung NVMe, 여유 555GB |
| 디스플레이 | 3440×1440 @ 143Hz |

### 판단

> "전혀 안 버거움. 여유 많음."

예상 부하를 **추정으로** 계산했다. 메이플 ~3GB, TFT ~3GB, FC온라인 ~2GB, 크롬 ~2GB = 약 10GB / 32GB.

### 무엇이 틀렸나

**실측 없이 추정했다.** 나중에 재보니 메이플 혼자 8.7GB를 썼다. 추정치의 3배였다.

### 부수적 혼선 — RAM 클럭

`Win32_PhysicalMemory.Speed` 가 2400MHz로 나와 XMP 미적용을 의심했다. 사용자가 "XMP 3600으로 켜져있다"고 정정했고, `ConfiguredClockSpeed` 를 보니 실제 3600MHz였다.

> **교훈:** `Speed` 는 SPD(JEDEC 기본값), `ConfiguredClockSpeed` 가 실제 동작 클럭이다.

## 2단계 — 메이플 단독 측정

사용자가 "사냥 중 프레임 드랍 + 작업관리자에서 90~100%"를 보고했다.

### 측정 (메이플만 실행)

| 지표 | 값 |
|---|---|
| RAM | 11.2 / 31.8 GB (**35%**) |
| CPU 전체 | **25.4%** |
| 코어별 최고 | 67.5% (100% 박힌 코어 없음) |
| GPU | 메이플 12% + dwm 22% + NexonPlug 9% ≈ 43% |

26샘플 전 구간 어디도 포화가 없었다.

### 판단

> "하드웨어 병목 아님. 작업관리자 오독."

### 무엇이 틀렸나

**측정 조건이 신고 조건과 달랐다.** 사용자는 "4개 동시"에서 90~100%를 봤는데, 나는 "메이플 단독"을 재고 있었다. 조건이 다르면 비교가 성립하지 않는데 그걸 놓쳤다.

사용자가 직접 지적했다.

> "지금 메이플만 실행해서 그런거같은데"

정확한 지적이었다.

### 이 단계에서 확인된 사실 (유효)

메이플 프로세스는 **nGuard(BlackCipher)** 가 보호한다. 외부에서 선호도를 읽으면 `0x0`, Priority는 공백이 반환된다. 실제 값이 아니라 **조회 자체가 차단**된 결과다.

## 3단계 — 4개 동시 측정, 증상 재현

### 측정 (8분, 59샘플)

| 지표 | 피크 | 평균 |
|---|---|---|
| CPU 전체 | **81.1%** | 66.2% |
| 단일 코어 최고 | **98.4%** | — |
| RAM | **88.3% (28.07GB)** | 86.8% |
| GPU 3D | **82.9%** | 56.8% |
| GPU VideoDecode | 0.0% | 0.0% |

### 앱별 분해

| 앱 | RAM 평균 | RAM 피크 |
|---|---|---|
| **MapleStory** | **8,384 MB** | **8,740 MB** |
| TFT/Riot (로비만) | 4,373 MB | 4,493 MB |
| FC ONLINE | 4,067 MB | 4,177 MB |
| Chrome | 2,556 MB | 2,709 MB |
| **합계** | **19,380 MB** | — |

### 판단 정정 2건

1. **"작업관리자 오독" → 취소.** RAM 88.3%는 실측값이고 사용자 관찰이 정확했다.
2. **"메모리 누수 아님, 5.6GB 평탄화" → 취소.** 8,740MB까지 증가했다. 시간당 약 3.7GB.

### 폐기된 가설 — 크롬 스트리밍

크롬에서 CHZZK 라이브 방송이 재생 중인 것을 발견하고 "GPU Video Decode 엔진을 포화시킨다"고 추정했다.

**`GPU VideoDecode = 0.0%` 전 구간.** 크롬 CPU도 1% 미만. 완전히 틀렸다.

### 이 단계의 방법론적 성과

GPU를 **엔진별로 분리 측정**(3D / VideoDecode / Copy / VideoProcessing / Compute)한 덕분에 가설을 즉시 반증할 수 있었다. 뭉뚱그린 "GPU 사용률"만 봤다면 놓쳤을 것이다.

## 4단계 — TFT 실제 게임 진입

3단계 측정에서 `tft_ingame` 이 59샘플 내내 0이었다. TFT는 클라이언트/로비만 떠 있었다.

### 프로세스명 문제

로거가 `League of Legends.exe` 를 찾고 있었는데 안 잡혔다. 창 제목을 훑어보니:

```
TFTClient-Win64-Shipping | TFT
```

**TFT는 별도 실행파일로 분리되어 있었다.** 롤 클라이언트를 공유하던 시절의 지식으로 만든 탐지 조건이 틀렸던 것.

### 측정 (28샘플, tft_ingame 28/28)

| 지표 | 값 |
|---|---|
| CPU 평균 / 피크 | 67.0% / 77.1% |
| `core_max` 평균 / 피크 | **81.5% / 95.3%** |
| RAM 평균 | 87.7% |
| **페이지파일 사용률** | **11.6% 고정 (min=max=avg)** |

### 결정적 발견 — 그리고 결정적 오판

**최고부하 코어의 분포:**

```
CPU12  2회   CPU13  6회   CPU14  9회   CPU15  8회   → E코어 23회 (82%)
CPU2   4회   CPU9   1회                            → P코어  5회
```

E코어가 평균 81.5%, 피크 95.3%로 상시 포화. P코어는 여유.

**여기서 두 가지를 판단했고, 하나는 맞고 하나는 크게 틀렸다.**

| 판단 | 결과 |
|---|---|
| "E코어 포화가 프레임 드랍 원인" | 부분적으로 맞음 (단, 범인 지목이 틀림 → 5단계) |
| **"페이지파일 11.6% 미동 = 스와핑 0 = RAM 병목 아님"** | **완전히 틀림 → 6단계** |

### 왜 틀렸나 — 지표 선택의 실패

`페이지파일 사용률 %` 은 **할당량 대비 비율**이다. 할당량이 함께 커지면 비율은 평탄하게 유지된다. 이건 *페이지 폴트 발생률*을 재는 지표가 **아니다.**

이 오판 때문에 "RAM 증설 불필요, 돈 쓰지 마"라고 조언했다. 정반대였다.

## 5단계 — P코어 고정 실험 (가설 검증, 그리고 기각)

E코어 가설을 검증하기 위해 메이플을 P코어에 묶어보기로 했다.

### 장애물 — 실행 중 변경이 거부됨

```
Exception setting "ProcessorAffinity": "Access is denied"
```

작업관리자에서도 동일하게 거부됐다. 메이플의 안티치트(nGuard)가 프로세스 핸들 권한을 제한하기 때문이다.

### 다른 경로 — 생성 시점 상속

**Windows는 프로세스를 만들 때 부모의 선호도를 자식에게 물려준다.** OS의 기본 동작이므로, 런처를 지정 선호도로 실행하면 게임이 그 값을 가진 채 시작된다.

```bat
start "Maple" /affinity 55 "C:\Nexon\Maple\GameLauncher.exe"
```

`0x55` = CPU 0, 2, 4, 6 (물리 P코어 4개, HT 형제 제외)

> **성격 명시:** CPU 선호도는 OS 스케줄러에 "이 스레드를 어느 코어에 올릴지" 알려주는 표준 설정이다. 게임 메모리·로직·통신에 전혀 관여하지 않고 게임플레이 이점도 없다. 여기서는 **성능 가설 검증을 위한 측정 수단**으로만 사용했으며, 아래에서 보듯 **결과는 효과 없음**이었다. 안티치트를 무력화하거나 게임 동작을 변경하는 용도로 쓰지 말 것.

### 상속이 실제로 작동하는지 검증

메이플 자체는 읽기가 막혀 확인이 불가능했다. 그래서 **보호되지 않은 프로세스로 대리 검증**했다.

```
notepad 선호도: 0x55  CPUs: 0,2,4,6
손자 프로세스(notepad) 선호도: 0x55  ← 부모→자식→손자 상속 확인
```

`GameLauncher.exe → MapleStory.exe` 도 같은 구조이므로 상속이 성립한다.

### 재측정 결과 (31샘플)

| 지표 | 적용 전 | 적용 후 | 판정 |
|---|---|---|---|
| E코어 최고부하 비율 | 23/28 (82%) | **28/31 (90%)** | ❌ 악화 |
| `core_max` 평균 | 81.5% | **81.5%** | ❌ 동일 |
| `core_max` 피크 | 95.3% | **100.0%** | ❌ 악화 |
| 90%+ 발생 | 5회 | 5회 | ❌ 동일 |

### 가설 기각

**개선이 0이었다.** 이유는 CPU 소비 분해로 명확해졌다.

| 프로세스 | CPU (16스레드 기준) | 환산 |
|---|---|---|
| **TFTClient** | **23.6%** | ~3.8 스레드 |
| **fczf (FC온라인)** | **16.3%** | ~2.6 스레드 |
| MapleStory | 6.2% | ~1.0 스레드 |
| LeagueClient + Ux | 5.7% | ~0.9 스레드 |
| chrome | <1% | — |

**메이플은 1스레드짜리였다.** E코어를 태우는 건 TFT와 FC온라인이었다. 메이플을 어디로 옮기든 E코어 포화는 그대로다.

오히려 메이플을 4코어로 좁혔는데 그 4코어를 TFT·FC온라인도 함께 쓰니 경합이 늘었을 가능성이 있다 (`core_max` 피크 95.3% → 100.0%와 일치).

> **교훈:** 가설을 세웠으면 *범인을 지목*하기 전에 *기여도를 분해*해야 한다. "E코어가 포화다"는 맞았지만 "메이플 때문이다"는 근거 없는 비약이었다.

## 6단계 — 프리징 재질문, 그리고 진짜 원인

사용자가 물었다.

> "현재 메이플이 프리징 걸리는 현상을 어떻게 완화할 수 있을까"

여기서 **프레임 드랍과 프리징을 분리**해서 보기 시작했고, 그제서야 올바른 지표를 집었다.

### 지표 교체

| 버렸다 | 집었다 |
|---|---|
| 페이지파일 사용률 % (할당량 대비) | **`\Memory\Pages Input/sec`** (하드 폴트 발생률) |
| — | **`Win32_Process.PageFileUsage` vs `WorkingSetSize`** (커밋 vs 상주 격차) |

### 측정 결과

```
MapleStory  상주(WorkingSet)  3,235 MB
            커밋(Private)    13,133 MB
            격차             10,070 MB   ← 디스크로 밀려남

Pages Input/sec   평균 161.5   최대 606.9
시스템 커밋       36.6 GB  /  물리 RAM 31.8 GB   ← 초과
페이지파일        사용 12,027 MB / 피크 16,036 / 할당 16,123 (99.5%)
```

### 원인 확정

```
게임 3개 커밋 합계 36.6GB  >  물리 RAM 31.8GB
        ↓
Windows가 백그라운드 앱 워킹셋을 페이지파일로 축출
        ↓
MapleStory 커밋 13GB 중 10GB가 디스크에
        ↓
다른 게임 보다가 메이플로 복귀
        ↓
축출된 10GB를 NVMe에서 되읽기 = 하드 페이지 폴트 폭주
        ↓
수 초간 멈춤 = 프리징
```

RAM 접근 ≈ 60~80ns vs NVMe 페이지 폴트 ≈ 50~100µs. **약 1000배 차이.**

### 추가 관찰 — 페이지파일이 천장을 치고 있었다

```
1차 확인: 피크 16,036 / 할당 16,123 = 99.5%
2차 확인: 피크 18,481 / 할당 18,490 = 99.95%   ← 16GB→18.5GB로 확장됨
```

자동 관리 페이지파일이 **가득 차서 확장을 반복**하고 있었다. 확장이 일어나는 순간마다 시스템이 멈춘다. 이것 자체가 독립적인 프리징 원인이다.

## 7단계 — "메모리 상한을 걸면 되지 않나?"

사용자의 합리적인 질문이었다. 답은 **아니오, 역효과**다.

### 그 시점 측정

```
물리 RAM 사용   13.1 / 31.8 GB   →  18.7 GB 여유
MapleStory      상주 2,419 MB  |  커밋 12,489 MB  |  밀려남 10,070 MB
```

**RAM이 18.7GB나 비어 있는데도 10GB가 밀려나 있었다.**

문제는 "메이플이 너무 많이 쓴다"가 아니라 **"메이플이 RAM에 너무 적게 남아있다"** 였다. 상한을 걸면 상주량을 더 줄이는 것이라 정확히 반대 방향이다.

| 제한 방식 | 결과 |
|---|---|
| 워킹셋 상한 (`SetProcessWorkingSetSize` max) | 트리밍 강화 → 폴트 증가 → **프리징 악화** |
| 커밋 상한 (Job Object) | 12.5GB 요구를 막음 → **할당 실패 → 크래시** |
| 메모리 정리 유틸 (`EmptyWorkingSet`) | 강제 트리밍 → **최악** |

덧붙여 Job Object 할당에 필요한 `PROCESS_SET_QUOTA` 는 nGuard가 이미 차단한 `PROCESS_SET_INFORMATION` 과 같은 계열이라, 애초에 적용도 안 될 가능성이 높다.

## 8단계 — RAM 32GB → 64GB

### 구매 판단

| 항목 | 선택 |
|---|---|
| 구성 | DDR4-2666 16GB × 4 = 64GB |
| 속도 | 3600 → 2666 (하락 감수) |
| 근거 | 대역폭 26% 손실 << 페이지 폴트 1000배 제거 |

**용량이 속도를 압도하는 상황**이었다. 커밋 36.6GB가 물리 RAM을 초과하는 한 페이징은 선택이 아니라 강제였다.

### 주의사항 (실제로 지킨 것)

- 기존 8GB 3600 4장 **전부 제거** (혼용 금지)
- 4장 **동일 파트넘버** — Samsung M378A2K43CB1-CTD
- 랭크 통일 (`2Rx8`), UDIMM non-ECC 확인
- BIOS에서 2666 / 1.20V (JEDEC 정규)

> 인텔 권고: 2DPC(채널당 2슬롯) 구성에서는 동일 파트넘버를 사용해야 목표 속도에 도달한다.

### 증설 후 측정 (4개 동시, 26샘플)

| 지표 | 증설 전 | **증설 후** |
|---|---|---|
| 물리 RAM | 28.07 / 31.8 GB (88.3%) | **30.2 / 63.8 GB (47%)** |
| 시스템 커밋 | 36.6 / 47.5 GB | 34.3 / 71.5 GB |
| **페이지파일 사용** | 12,027 MB | **0 MB (전 샘플)** |
| **페이지파일 피크** | 18,481 MB | **0 MB** |
| 메이플 상주 / 커밋 | 2,419 / 12,489 (19%) | **7,823 / ~8,100 (96%)** |

**부팅 이후 페이지파일 사용량 0.** 스왑이 물리적으로 일어나지 않는다. 프리징 메커니즘 소멸.

### `Pages Input/sec` 는 왜 0이 아닌가

증설 후에도 스파이크가 찍혔다 (1168 / 1209 / 3155 / 2319).

**그 샘플들 전부 `pf_used = 0`.** 이 카운터는 페이지파일뿐 아니라 **파일 기반 읽기**(게임 에셋, DLL 매핑)도 센다. 사냥터 이동·TFT 라운드 전환 시의 정상적인 스트리밍이다.

> **교훈:** 카운터 이름만 보고 해석하면 안 된다. `Pages Input/sec` 단독으로는 스와핑 여부를 판정할 수 없고, `PageFileUsage` 와 함께 봐야 한다.

### CPU 지표는 그대로

| 지표 | 증설 후 |
|---|---|
| `core_max` 피크 | **98.5%** |
| E코어 최고부하 | 여전히 높음 |

**예측한 대로였다.** RAM은 CPU 병목에 아무 영향이 없다.

## 9단계 — Windows 설정 4개

RAM과 무관하게 남아있던 설정 문제를 정리했다.

| 항목 | 변경 전 | 변경 후 | 근거 |
|---|---|---|---|
| HAGS (`HwSchMode`) | 1 (꺼짐) | **2** | GPU 스케줄링 지연 감소 |
| MPO (`OverlayTestMode`) | 미설정 (활성) | **5** | DX11 창모드 스터터링의 알려진 원인 |
| GameDVR | 1 | **0** | 백그라운드 녹화 오버헤드 |
| 전원 계획 | 균형 조정 (최소 5%) | **고성능 (최소 100%)** | 클럭 램프업 지연 제거 |

재부팅 후 4개 전부 적용 확인.

### 부수적 발견 — 메이플은 DirectX 11

```
C:\Nexon\Maple\Gr2D_DX11.dll     ← DX11 2D 렌더러
(DX9 렌더러 파일 없음)
```

DX11은 **드로우콜이 단일 스레드에 몰린다.** 메이플이 CPU 1스레드에 묶이는 구조적 이유이고, 코어를 늘려도 렌더 스레드 하나가 병목으로 남는 이유다. MPO 비활성화가 유효한 이유도 같은 맥락(DX11 창모드).

## 최종 정리

### 원인 분리

| 증상 | 원인 | 상태 |
|---|---|---|
| **프리징** | 커밋 36.6GB > 물리 RAM 31.8GB → 하드 페이지 폴트 | ✅ **해결** |
| **프레임 드랍** | P코어 6개 vs 활성 8.6스레드 → E코어 포화 | ❌ 미해결 |

### 남은 과제

```
P코어 6개  vs  상시 활성 8.6 스레드
TFT 3.8 + FC온라인 2.6 + 메이플 1.0 + LeagueClient 0.9 + dwm 0.3
```

선택지:

1. **게임 3개 → 2개** — 공짜. TFT가 CPU·GPU 모두 1위로 가장 무겁다
2. **프레임타임 측정** (MSI Afterburner + RTSS) — **아직 미실시.** 드랍의 정체를 확정하는 유일한 방법
3. **CPU + 보드 교체** — 14700K (8P+12E) + B760M DDR4. 현재 B660M DS3H는 6+2+1 페이즈 VRM이라 253W i7을 감당 못 한다. DDR4 64GB는 그대로 사용 가능 (LGA1851/DDR5로 가면 RAM 폐기)

> 3번은 **프레임타임 측정 전에는 권장하지 않는다.** CPU 쪽으로 실행한 유일한 실험(P코어 고정)이 개선 0이었으므로 인과가 확립되지 않았다.

## 이 과정에서 얻은 교훈

1. **추정으로 결론 내지 말 것.** 1단계에서 메이플을 3GB로 추정했는데 실제는 8.7GB였다.

2. **측정 조건을 신고 조건과 일치시킬 것.** 2단계에서 "메이플 단독"을 재고 "4개 동시"를 판정했다.

3. **지표가 무엇을 재는지 정확히 알 것.** 4단계의 오판은 `페이지파일 사용률 %`(할당량 대비)를 폴트 발생률로 착각한 데서 나왔다. 지표 하나 바꾸자 원인이 즉시 드러났다.

4. **가설의 범인 지목 전에 기여도를 분해할 것.** "E코어 포화"는 맞았지만 "메이플 탓"은 비약이었다. CPU 분해를 먼저 했으면 5단계 실험 자체가 불필요했다.

5. **증상을 뭉뚱그리지 말 것.** 프리징과 프레임 드랍은 원인이 완전히 달랐다. 분리해서 보기 시작한 6단계에서야 진짜 원인이 나왔다.

6. **사용자의 관찰을 함부로 기각하지 말 것.** "작업관리자 오독"이라 판정했지만 실측해보니 사용자가 본 수치가 정확했다.
